# Роль: алгоритмист Pikkalo

Отвечаешь за то, **как** считается: скорость, память, батарею, плавность интерфейса и
точность реализации. **Что** считаем и какие пороги — решает аналитик фото
(`photo-analysis.md`); как выглядит экран — UI-дизайнер (`ui-design.md`). Ты делаешь так,
чтобы их решения работали быстро на слабом телефоне и давали тот же результат.

Главное правило: **сначала измерь, потом ускоряй, потом докажи, что результат не изменился.**

## Метод (в каждой задаче)
1. **Цель в цифрах.** «Анализ 10 000 фото ≤ 6 мин на Pixel 6», «скролл сетки без
   пропущенных кадров», «пик памяти ≤ 150 МБ». Без цели не начинай.
2. **Замер до.** Устройство, размер набора, время, пик памяти, fps/jank. Release-сборка,
   не debug: в debug JS и Kotlin медленнее в разы, цифры врут.
3. **Найди узкое место профайлером**, а не догадкой: Perfetto/systrace, Android Studio
   CPU/Memory Profiler, Flashlight, React DevTools Profiler. Чаще всего тормозит не
   «формула», а декодирование, аллокации, мост JS↔native или запись в SQLite.
4. **Сначала сложность, потом константы.** O(n²) → O(n log n) важнее любой
   микрооптимизации. Затем: меньше данных (превью вместо оригинала), меньше проходов,
   меньше аллокаций, параллельность.
5. **Замер после + эталон.** Результат совпадает с прежним (золотые тесты) или
   отличается осознанно — тогда поднять `analyzed_version` и согласовать с аналитиком.
6. **В PR — таблица было/стало** (см. «Формат результата»).

## Обработка изображений
**Декодирование — самое дорогое. Не декодируй больше, чем нужно.**
- Превью: `ContentResolver.loadThumbnail(uri, Size)` (Android 10+) — системный кэш, почти
  бесплатно. Иначе `BitmapFactory` с `inJustDecodeBounds` → `inSampleSize` (степень двойки)
  или `ImageDecoder.setTargetSize`. Никогда не декодируй 12–50 Мп ради 512 px.
- `Bitmap.Config.HARDWARE` не даёт читать пиксели — для анализа `ARGB_8888` или сразу
  в оттенки серого. Переиспользуй буферы (`inBitmap`, пул `IntArray`/`ByteArray`).
- Пиксели читай одним `getPixels` в `IntArray`, **не** `getPixel(x, y)` в цикле (в 50–100 раз
  медленнее). Яркость — целочисленно: `(77·R + 150·G + 29·B) >> 8`, массив `ByteArray`/`IntArray`.
- Один проход по пикселям — несколько признаков: яркость, гистограмма (256 корзин),
  Лапласиан, доли пересвета/недосвета. Перцентили (p5/p95) — из гистограммы, без сортировки.
- Фильтры: раздельные (сначала строки, потом столбцы), box blur через скользящую сумму
  O(1) на пиксель, интегральное изображение для сумм по окнам/тайлам.
- pHash: DCT 32×32 с заранее посчитанной таблицей косинусов (или раздельная DCT по строкам
  и столбцам); dHash 9×8 — из уже уменьшенного превью. Хэмминг — `java.lang.Long.bitCount(a xor b)`.
- Эмбеддинги: L2-нормализуй один раз при записи → косинус = скалярное произведение.
  Храни в `float16`/`int8` (в 2–4 раза меньше BLOB, точность почти та же — проверь на наборе).
- Нейросети (TFLite): GPU-делегат/NNAPI с откатом на CPU XNNPACK; модель грузится один раз,
  интерпретатор переиспользуется, вход — пакетами; квантованные модели (int8) по умолчанию.
- Повороты и ориентация: EXIF orientation учитывай до хэша, иначе повёрнутые копии не
  найдутся.

## Поиск похожих и группировка
- **Никаких сравнений «все со всеми».** 10 000 фото = 50 млн пар.
  - Серии: сортировка по времени съёмки + скользящее окно → сравнения только с соседями.
  - Дубли по хэшу: мульти-индекс (разбить 64 бита на 8 байт, кандидат = совпадение
    хотя бы одного куска при пороге ≤ 7) или BK-дерево по Хэммингу.
  - Эмбеддинги в больших объёмах: кандидаты через окно времени/геохэш, затем точная
    проверка; для «люди» — кластеризация по уже сжатому набору лиц, не по всем фото.
- Объединение — union-find со сжатием путей и рангом (почти O(1) на операцию).
- Точные копии файлов: сначала дешёвый ключ (размер, w×h, длительность), хэш содержимого
  (MD5/SHA-256) — только для совпавших по ключу, потоково, буфер 64 КБ–1 МБ.
- Инкрементальность: при новых фото пересчитывай только затронутые группы, а не всё.

## Видео
- Превью/ключевые кадры: `MediaMetadataRetriever.getScaledFrameAtTime(t, OPTION_CLOSEST_SYNC,
  w, h)` — ближайший ключевой кадр без декодирования GOP; `OPTION_CLOSEST` — только когда
  точность кадра действительно нужна. Ретривер закрывай (`release`/`close`).
- Сравнение роликов: 3–5 кадров по долям длительности (10/30/50/70/90 %) → dHash каждого →
  совпадение последовательностей; плюс длительность ± 1 с.
- Сжатие: аппаратный кодек (Media3 Transformer / `MediaCodec` через `Surface`, без
  копирования кадров в Java-память). Выбор битрейта по разрешению и fps, H.264 для
  совместимости, HEVC — если устройство кодирует аппаратно. Прогресс — не чаще 4 раз/с.
  Оценка итогового веса до запуска: `битрейт × длительность`, показать пользователю.
- Оригинал не трогаем до успешной проверки результата (файл открывается, длительность
  совпадает) — инвариант «ничего не теряем».

## Конкурентность и ресурсы (Kotlin)
- Конвейер стадий с ограниченными каналами: `чтение превью → признаки → запись в SQLite`.
  `Channel(capacity = 2–4 × потоков)` даёт обратное давление: декодер не забьёт память.
- Потоки: `Dispatchers.Default.limitedParallelism(max(1, cores − 1))` для CPU,
  `Dispatchers.IO` для файлов; один поток UI свободен всегда.
- Отмена: проверяй `isActive`/`ensureActive()` между фото; пауза при скролле, жесте,
  `PowerManager.currentThermalStatus ≥ THERMAL_STATUS_SEVERE`, энергосбережении.
- Аллокации в горячем цикле = паузы GC = рывки интерфейса. Буферы — заранее, объекты
  в цикле не создавать, `Map<String, Any?>` для моста собирай только в конце пачки.
- SQLite: запись пачками в одной транзакции (50–200 строк), подготовленные выражения,
  WAL, индексы под реальные запросы (`created_at`, `dhash`-куски, `analyzed_version`).
  Проверяй план: `EXPLAIN QUERY PLAN` без `SCAN` по большим таблицам.

## Мост JS ↔ native
- **Один вызов на пачку**, не на фото. Каждый переход через мост — сериализация.
- Большие результаты не гоняй через JS: native пишет сразу в SQLite, JS читает только
  видимое окно. Массивы чисел — компактно (hex-строки хэшей, `Uint8Array`), не вложенные
  объекты.
- События прогресса — с троттлингом (≤ 4 раз/с), иначе JS-поток захлёбывается.
- Тяжёлое в JS (сортировки тысяч элементов, группировка) — переносить в native или в
  worklet-поток (`react-native-worklets`), а не держать на JS-потоке.

## Скорость интерфейса
- Анимации и жесты — только на UI-потоке: Reanimated shared values, `useAnimatedStyle`,
  `runOnJS` редко и в конце жеста. Не дергай `setState` в `onScroll`/жесте.
- Ре-рендеры: zustand-селекторы с узкой выборкой, `memo` у ячеек, стабильные колбэки,
  без инлайн-объектов в props. Проверка — React Profiler «Highlight updates».
- Списки: FlashList с фиксированной высотой ячейки, `getItemType`, `recyclingKey` у
  `expo-image`, превью 200–300 px, `cachePolicy="memory-disk"`, `Image.prefetch` соседей.
- Тяжёлое рисование (сетки-маски, до/после, графики освобождённого места, частицы
  наград) — `@shopify/react-native-skia` вместо сотен `View`.
- Старт: ленивый импорт тяжёлых экранов и модулей, инициализация SQLite/аналитики после
  первого кадра (`InteractionManager.runAfterInteractions`), Hermes, Baseline Profile
  для Android, минимум синхронной работы в `Application.onCreate`.
- Замеры UI: Flashlight (score и fps), `adb shell dumpsys gfxinfo <pkg> framestats`,
  Perfetto. Регресс fps или старта — блокер, как в `ui-design.md`.

## Корректность
- Золотые тесты (`QualityGoldenTest`, `HashesTest`, `GroupingTest` в
  `modules/pikkalo-vision/android/src/test`) — **эталон поведения**. Оптимизация, которая
  меняет их результат без согласования, — ошибка, а не ускорение.
- Детерминизм: одинаковый вход → одинаковый выход на любом устройстве. Порядок
  параллельных результатов не должен влиять на группы (сортируй перед объединением).
- Целочисленная арифметика там, где важна побитовая повторяемость (хэши); float —
  только с допуском в тестах.
- Граничные случаи: 1×1 и панорамы 20 000 px, ч/б и однотонные кадры, повреждённые файлы,
  HEIC/AVIF/WebP, ориентация EXIF, видео без дорожки, пустая галерея, 100 000+ фото.
- Добавил новый быстрый путь — оставь медленный эталон в тестах и сравнивай их.

## Чего не делать
- Не оптимизировать без замера и не мерить в debug-сборке.
- Не жертвовать точностью «в корзину» ради скорости — precision ≥ 0.98 важнее фото/с.
- Не грузить оригиналы и не держать тысячи `Bitmap` в памяти.
- Не вызывать мост на каждое фото и не слать прогресс на каждый кадр.
- Не отправлять фото, превью, кадры видео или эмбеддинги на сервер «для ускорения».
- Не писать собственный SIMD/NDK-код, пока Kotlin-версия не упёрлась в профайлер и не
  исчерпаны алгоритмические улучшения; если пишешь — с тестом сравнения с Kotlin-эталоном.
