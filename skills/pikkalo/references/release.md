# Выпуск обновления (релиз APK)

Как устроено: `scripts/release.sh` в репозитории приложения собирает release-APK
(`arm64-v8a`), подписывает постоянным ключом `~/.pikkalo/pikkalo-release.jks` (пароли в
`~/.gradle/gradle.properties`), сверяет SHA-256 сертификата, создаёт релиз `v0.1.<N>` в публичном
репозитории `IlyaKovalchukKIS/pikkalo-releases` и загружает туда APK и `latest.json`. Приложение
раз в 12 ч читает `…/releases/latest/download/latest.json`, проверяет размер, SHA-256, пакет и
сертификат и предлагает установить поверх (TASK-120). Магазинов нет, TestFlight/Play не используем.

Пользователь получает **всё, что помечено Latest** в `pikkalo-releases`, автоматически. Поэтому
релиз — необратимое действие: его запускает владелец или Claude по прямому «выпускай», не по ходу задачи.

## Чем это отличается от сборки для проверки
- `../builds/pikkalo-0.1.0-<sha>.apk` — промежуточные APK для эмулятора (отладочная подпись,
  `versionName` 0.1.0). Пользователям их не даём: подпись другая, поверх релиза они не встанут.
- Релиз — только через `scripts/release.sh`. Вручную `gh release create` / правка `latest.json` — нельзя:
  пропускаются проверка подписи и согласованность `versionCode` ↔ имя APK ↔ `latest.json`.

## Чек-лист релиза
Отмечай фактически сделанное; что нельзя проверить — так и напиши, не ставь галочку.

### 1. Исходник
- [ ] Ветка `main`, `git status` чистый, `git pull --ff-only` выполнен, все PR релиза влиты.
      С фича-ветки не выпускаем: `versionCode` считается по коммитам, а код у пользователей
      должен совпадать с `main`.
- [ ] В корне нет устаревшего `release-notes.json` от прошлого релиза (скрипт молча возьмёт его).
- [ ] `gh auth status` — есть доступ на запись в `pikkalo-releases`.

### 2. Версия и номер сборки
- [ ] `versionCode` задаёт скрипт: `git rev-list --count HEAD`, но не меньше последнего
      опубликованного + 1. Вручную `PIKKALO_VERSION_CODE` — только если нужен конкретный номер, и он
      **строго больше** последнего (`gh release list -R IlyaKovalchukKIS/pikkalo-releases -L 5`).
      Android не установит APK с меньшим или равным `versionCode`.
- [ ] Номер никогда не переиспользуем, даже если релиз удалён.
- [ ] `app.json` → `version` остаётся `0.1`, `applicationId` = `app.pikkalo` — не трогать
      (смена пакета = новое приложение, обновление поверх невозможно).

### 3. Проверки до сборки
- [ ] `npm run typecheck`, `npm run lint`, `npm test` — зелёные (скрипт запустит их сам,
      но прогони заранее, чтобы не ждать Gradle ради падения линта).
- [ ] Затронут натив (`modules/pikkalo-vision`, плагины) → `npm run test:native`.
- [ ] Новая нативная библиотека с рефлексией → keep-правило в `extraProguardRules` (`app.json`),
      см. «Грабли Android release» в `team-routing.md`.

### 4. Данные и совместимость
- [ ] Миграции SQLite (`src/db/migrations.ts`) — **только дописываются в конец**. Уже выпущенную
      строку не править и не удалять: на устройствах она применена, `PRAGMA user_version` её помнит.
- [ ] `migrate()` падает, если `user_version` базы больше известной (`Unsupported database
      version`), значит **откат на старый APK с новой базой невозможен** — миграции должны быть
      безопасны с первой попытки.
- [ ] `allowBackup: false`: данные живут только на телефоне, потерянную при обновлении базу не
      вернуть. Обновление поверх — обязательный пункт смоука (п. 6).
- [ ] Изменён формат `latest.json` или клиент обновлений (`src/updates/`) → старые версии
      должны продолжать его парсить (`parseRelease` отвергает неизвестный формат — тогда обновления
      у пользователей просто перестанут приходить).
- [ ] `minVersionCode` поднимаем, только если старые версии вредят данным или не работают;
      по умолчанию — не трогаем.

### 5. Заметки о версии (changelog)
- [ ] `--notes-ru` и `--notes-en` (по флагу на пункт) или временный `release-notes.json`
      (`{ "notes": { "ru": [...], "en": [...] }, "minVersionCode": 0 }`).
- [ ] 2–4 пункта для человека, языком `copy-marketing.md`: что стало лучше для пользователя, а не
      имена задач и коммитов. До 500 символов на пункт, ru и en по смыслу совпадают.
- [ ] Первые 2–3 пункта видны на карточке «Доступна версия» — самое важное первым.

#### Пользователь должен прочитать, что изменилось
Заметки — не формальность для GitHub: пользователь читает их в приложении в трёх местах.
- **До установки** — карточка «Доступна версия» (первые 3 пункта из `latest.json`).
- **После установки** — при первом запуске новой версии один раз показывается «Что нового».
  Если пользователь пропустил версии (стоял 0.1.190, поставил 0.1.200), показываем заметки
  **всех** пропущенных версий, новые сверху. После чистой установки не показываем.
- **В любой момент** — Кабинет → «Что нового»: полная история версий.

Поэтому:
- [ ] История живёт в приложении: `src/updates/changelog.json` (`[{ versionCode, date, ru: [...], en: [...] }]`,
      новые сверху). `scripts/release.sh` сам дописывает туда запись выпускаемой версии из
      `--notes-ru/--notes-en` **до сборки**, чтобы она попала в этот же APK. Вручную записи
      уже выпущенных версий не правим — кроме исправления опечаток.
- [ ] Каждый пункт понятен без контекста: человек, пропустивший 5 версий, читает их подряд.
      Не «Исправлен баг #123», а «Свайп в корзину больше не отменяет прошлое „Оставить“».
- [ ] В релизе есть хотя бы один пункт, заметный пользователю. Только внутренние правки →
      честно: «Стабильнее и быстрее работает анализ», без выдумок.
- [ ] Смоук (п. 6): после обновления поверх показалось «Что нового» с этой версией,
      в Кабинете она первая в истории; после `pm clear` окно не появилось.
- [ ] После публикации (п. 8) запись в `changelog.json` закоммичена в `main`: иначе следующий
      релиз потеряет её из истории.

### 6. Сборка и ручной смоук (до публикации)
Скрипт сразу публикует, поэтому смоук делаем на той же release-сборке заранее:
`npx expo prebuild --platform android --no-install && (cd android && ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a)`
с тем же `PIKKALO_VERSION_CODE`.
- [ ] Сборка без ошибок; `apksigner verify --print-certs` — сертификат `4923B44E…8290`.
- [ ] **Обновление поверх** прошлого релиза на эмуляторе/телефоне с данными (`adb install -r`):
      база открылась, прогресс, награды, Люди, Места, подключённый Диск на месте.
- [ ] **Чистая установка** (`pm clear`): онбординг → доступ к фото → все вкладки, без падений.
- [ ] Основные сценарии: разбор группы (дубли/серия), свайп-разбор, «в корзину» → «Отменить»,
      вкладка «Медиа», анализ продолжается после сворачивания.
- [ ] Ограниченный доступ к фото и офлайн — экран не пустой и не падает.
- [ ] `adb logcat -b crash` пуст.
- [ ] Затронутые задачей экраны — отдельно, по критериям приёмки их TASK.

### 7. Публикация
- [ ] `scripts/release.sh --notes-ru "…" --notes-en "…"` из корня репозитория приложения.
      Скрипт повторяет проверки, сборку, сверку сертификата, загружает APK **раньше** `latest.json`.
- [ ] Упал на загрузке — перезапусти тот же скрипт с тем же `PIKKALO_VERSION_CODE`: релиз
      переиспользуется, `--clobber` перезапишет ассеты. Не создавай второй номер.
- [ ] Проверка: релиз помечен Latest, в нём ровно `pikkalo-0.1.<N>.apk` и `latest.json`;
      `curl -sL https://github.com/IlyaKovalchukKIS/pikkalo-releases/releases/latest/download/latest.json`
      отдаёт `versionCode` = N.
- [ ] На устройстве с прошлой версией: Кабинет → «Проверить обновления» → скачивание → проверка →
      установка поверх → в Кабинете «Версия 0.1.<N>».

### 8. После публикации
- [ ] Тег в репозитории приложения на собранный коммит: `git tag v0.1.<N> && git push origin v0.1.<N>`
      (в `pikkalo-releases` кода нет — только по этому тегу видно, из чего собран APK).
- [ ] Опубликованный APK — в `../builds/pikkalo-0.1.<N>.apk`
      (копия `android/app/build/outputs/apk/release/app-release.apk`) вместе с
      `android/app/build/outputs/mapping/release/mapping.txt` как `pikkalo-0.1.<N>-mapping.txt`:
      без него стеки падений из release не расшифровать.
- [ ] `release-notes.json` удалён/не закоммичен.
- [ ] Запись: дата, версия, что вошло (PR), ссылка на релиз — в лог владельца; существенное
      (поднят `minVersionCode`, изменён формат обновлений) — строка в `docs/DECISIONS.md`.
- [ ] Ответ владельцу: номер версии, ссылка, что проверено, что не проверено.

## Откат
Понизить версию нельзя: Android не ставит меньший `versionCode`, а `migrate()` не откроет новую базу
старым кодом. Откат = остановить раздачу + выпустить исправление **с большим номером**.
1. **Остановить раздачу сразу**: `gh release edit v0.1.<N> --repo IlyaKovalchukKIS/pikkalo-releases --prerelease`.
   и явно вернуть Latest прошлому: `gh release edit v0.1.<прошлый> --repo IlyaKovalchukKIS/pikkalo-releases --latest`.
   Кто ещё не обновился — не получит плохую версию. Проверь `curl … latest.json` → прошлый `versionCode`. Релиз не удаляй: это обратимо, удаление — нет.
2. **Исправление**: `git revert` плохих коммитов (или точечный фикс) на `main` через PR, весь чек-лист
   выше, новый релиз `v0.1.<M>`, M > N. Заметка честная: «Исправили …».
3. Сломанная миграция уже применилась у части пользователей → чинить **новой** миграцией, которая
   приводит к верной схеме и старую, и испорченную базу. Не редактировать выпущенную.
4. Плохая версия портит данные или не запускается → в исправлении поднять `minVersionCode` до M,
   чтобы карточку обновления нельзя было отложить.
5. После — строка в `docs/DECISIONS.md`: что сломалось, почему проверки не поймали, какой пункт
   добавлен в этот чек-лист.
