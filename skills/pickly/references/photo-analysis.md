# Роль: аналитик фото Pickly

Задача — находить то, что можно разобрать, и честно подсказывать лучший кадр. Ошибка
«предложили в корзину хорошее фото» стоит дороже, чем «не нашли дубль». Поэтому
**точность важнее полноты**: при сомнении — не предлагаем, а просим выбрать.

Всё выполняется **на устройстве**. Ни фото, ни превью, ни эмбеддинги, ни лица не уходят
на сервер.

## Архитектура
```
Источники ─► Индексатор ─► Извлечение признаков ─► Группировка ─► Оценка ─► Подсказки в UI
(галерея,     (инкремент.,   (хэши, эмбеддинги,      (дубли, серии,   (лучший    (с объяснением
 Я.Диск)       SQLite)        качество, лица, OCR)    категории)       кадр)      и уверенностью)
```

Тяжёлые вычисления — в собственном Expo-модуле `modules/pickly-vision` с одним
TS-интерфейсом. **Сначала Android (Kotlin)**, Swift — при выходе iOS. Платформенные движки
бесплатны, быстры и не требуют своих моделей:

| Признак | iOS (Vision) | Android |
|---|---|---|
| Эмбеддинг сцены | `VNGenerateImageFeaturePrintRequest` | TFLite MobileNetV3 / MobileCLIP-S0 через `react-native-fast-tflite` или в модуле |
| Лица, глаза, улыбка | `VNDetectFaceLandmarksRequest`, `VNDetectFaceCaptureQualityRequest` | ML Kit Face Detection (`eyeOpenProbability`, `smilingProbability`) |
| Текст (OCR) | `VNRecognizeTextRequest` | ML Kit Text Recognition v2 |
| Эмбеддинг лица (люди) | TFLite MobileFaceNet | TFLite MobileFaceNet |
| Резкость, экспозиция, dHash | вычисляем в модуле по превью 256–512 px | так же |

Работаем по **превью** (длинная сторона 512 px для качества, 64 px для хэша), а не по
оригиналам — в 20–50 раз быстрее.

## Индексация
- Ассеты галереи: `expo-media-library` постранично (`first: 500`, `after`), инкрементально
  по `modificationTime`; подписка на изменения библиотеки.
- Яндекс Диск: `GET /v1/disk/resources/last-uploaded` и `/resources/files?media_type=image,video`
  постранично; поля `md5`, `sha256`, `size`, `preview`, `exif`, `photoslice_time`.
  Превью качаем с параметром размера и кэшируем на устройстве, не на сервере.
- Хранилище: `expo-sqlite`. Таблицы: `assets` (id, source, uri, created_at, size, w, h,
  subtype, album, gps, is_favorite, analyzed_version), `features` (asset_id, dhash,
  embedding BLOB, sharpness, exposure, faces_json, ocr_chars, quality), `groups`,
  `decisions` (что пользователь оставил/убрал — для персонализации и отмены).
- `analyzed_version` — при смене алгоритма пересчитываем только устаревшее.

## Планирование работы
- Пачки по 16–32 превью, после каждой — отдать поток UI (`InteractionManager` / пауза).
- Пауза при: активном скролле/жесте, `thermalState >= serious`, режиме энергосбережения,
  заряде < 20% без зарядки.
- Фон: `expo-background-task` (iOS BGProcessingTask, Android WorkManager) — только на зарядке.
- Приоритет: сначала свежие 30 дней и крупные файлы (быстрый первый результат ≤ 10 с),
  потом остальное. UI показывает готовое сразу: «Уже нашли 340 МБ, ищем дальше».

## Группировка

### Точные дубли
- Яндекс Диск: совпадение `sha256`.
- Галерея: совпадение (размер, w, h, created_at) → затем подтверждение по dHash = 0.
- Между источниками: dHash по превью + совпадение даты съёмки ± 2 с.
Подсказка: оставить один (лучше в оригинальном качестве, с геометкой, в избранном).

### Видео (первый релиз — без анализа содержимого)
- «Тяжёлые видео»: сортировка по размеру, показ длительности и веса, превью-кадр.
- Точные копии видео: Диск — `sha256`; телефон — (размер, длительность, дата) + MD5 по
  требованию в фоне; между источниками — MD5 телефона = `md5` Диска.
- Похожие ролики по ключевым кадрам — следующий релиз.

### Почти дубли и похожие кадры (серии)
1. Кандидаты: соседние по времени съёмки, разрыв ≤ 10 с внутри цепочки (серийная съёмка,
   «щёлкнул пять раз»), плюс окно до 2 мин при одной геолокации.
2. Подтверждение: pHash Хэмминг ≤ 6 **и** dHash ≤ 10 (проверено в PhotoSeparator) **или**
   косинусная близость эмбеддингов ≥ T_sim. Поиск кандидатов — мульти-индекс по 8 байтам pHash.
3. `T_sim` калибруется на эталонном наборе отдельно для iOS feature print и Android-модели
   (стартовые значения: iOS distance ≤ 0.35, cosine ≥ 0.90 — **проверить на наборе**).
4. Связные компоненты, серия ≥ 2 кадров; серии > 30 кадров дробим по времени.

### Категории
| Категория | Признаки |
|---|---|
| Скриншоты | iOS: `mediaSubtypes` содержит `screenshot`; Android: альбом/путь `Screenshots`; размер = разрешению экрана, нет EXIF камеры |
| Картинки из WhatsApp | путь/альбом `WhatsApp Images`, имя `IMG-YYYYMMDD-WA####`, нет EXIF камеры, длинная сторона ≤ 1600 px. Подкатегория «открытки»: много текста (OCR ≥ 15 символов крупным кеглем) + высокая насыщенность. Предлагаем только старше 30 дней |
| Документы и чеки | OCR ≥ 80 символов, высокая контрастность, мало цветов |
| Размытые/случайные | резкость < порога И нет лиц И одиночный кадр (не серия); снимки «в карман» — очень тёмные/однотонные |
| Видео | большие файлы, длинные, дубли; показываем вес крупно |
| Люди | кластеризация эмбеддингов лиц (HDBSCAN/агломеративная, cosine), **только после явного согласия** пользователя; имена — локально |
| Места | GPS из EXIF → кластеры по geohash (точность 5–6) → поездки (далеко от «дома» + дни подряд). Названия городов — по встроенному офлайн-справочнику (GeoNames cities15000), без сетевого геокодера |

## Выбор лучшего кадра

### Оценка каждого кадра серии (0..1)
```
quality = 0.30·sharp + 0.15·exposure + 0.35·faces + 0.10·composition + 0.10·technical
```
- **sharp** — дисперсия Лапласиана по превью 512 px, нормированная внутри серии (min-max):
  важна относительная резкость, а не абсолютная.
- **exposure** — штраф за пересвет/недосвет: доля пикселей в 2% краях гистограммы.
- **faces** (если есть лица; иначе вес переносится на sharp/composition):
  среднее по лицам `eyesOpen·0.4 + smile·0.2 + faceQuality·0.4`; если хоть у одного
  закрыты глаза (< 0.3) — сильный штраф ×0.5.
- **composition** — главный объект/лица не обрезаны краем кадра, горизонт ровный (± 3°).
- **technical** — разрешение, HDR/Live Photo, отредактировано пользователем (+), уже в
  избранном (+ сильный бонус).

### Правила решения
- Избранные, отредактированные, скрытые и фото из общих альбомов **никогда** не
  предлагаем в корзину автоматически.
- Если разрыв между первым и вторым местом < 0.05 — уверенность низкая: показываем
  оба как «лучшие», ничего не отмечаем в корзину, текст «Выберите сами — оба хороши».
- Объяснение выбора — 1–2 причины с наибольшим вкладом, человеческими словами
  (формулировки — у маркетолога): «самый резкий», «у всех открыты глаза», «лучше свет».
- Персонализация: если пользователь часто меняет наш выбор, сдвигаем веса в его сторону
  (локально, по таблице `decisions`).

## Перемещение в корзину (реализация инварианта)
| Источник | Как | Важно |
|---|---|---|
| iOS | `PHAssetChangeRequest.deleteAssets` (так работает `MediaLibrary.deleteAssetsAsync`) | Уходит в «Недавно удалённые», система показывает подтверждение. Пакетируй: один диалог на серию/сессию |
| Android 11+ | `MediaStore.createTrashRequest(…, true)` в модуле `pickly-vision` | **Не** использовать `createDeleteRequest` — это безвозвратно. Проверь, что делает `deleteAssetsAsync` в текущей версии Expo, и не используй его для корзины |
| Android ≤ 10 | Корзины в системе нет | Своя корзина: переносим файл в скрытую папку приложения на 30 дней с возможностью вернуть; честно пишем об этом |
| Яндекс Диск | `DELETE /v1/disk/resources?path=…&permanently=false` | Асинхронная операция для папок — опрашивай статус; восстановление `PUT /v1/disk/trash/resources/restore` |

Каждое действие пишется в `decisions` — это основа «Отменить» и статистики «освобождено».

## Качество (обязательно перед изменением алгоритма)
- Эталонный набор: ≥ 2 000 фото разных сценариев (портреты, группы, пейзажи, еда, дети,
  питомцы, ночь, скриншоты, WhatsApp-картинки), размечено «лучший кадр» и «можно убрать».
  Хранится локально у разработчика, в репозиторий — только разметка и скрипт.
- Метрики и пороги приёмки:
  - precision предложений «в корзину» ≥ 0.98;
  - совпадение лучшего кадра с человеком: top-1 ≥ 0.75, top-2 ≥ 0.90;
  - recall дублей ≥ 0.90;
  - скорость: ≥ 30 фото/с на iPhone 12 / Pixel 6 по превью.
- В PR с изменением порогов — таблица метрик было/стало. Ухудшение precision — блокер.

## Чего не делать
- Не отправлять фото/превью/эмбеддинги в облачные модели — даже «для улучшения качества».
- Не анализировать оригиналы, когда хватает превью.
- Не блокировать UI-поток вычислениями.
- Не показывать «оценку качества» числом — пользователю нужны причины, а не баллы.

## Перенос из PhotoSeparator
Берём код, а не инструкции проекта. Источник — `android/shared/src/commonMain/kotlin/ru/photoseparator/probe/`.
Чистый Kotlin без зависимостей от Compose/Room переносится в `modules/pickly-vision/android`
почти дословно; тесты (`commonTest`) — вместе с кодом, как эталон поведения.
| Что | Откуда | Как переносим |
|---|---|---|
| Точные дубли (union-find по sha256/md5+размер), мост через MD5 телефона | `analysis/Grouping.kt` → `exactGroups` | как есть, `FileEntity` → лёгкий data class модуля |
| Похожие (pHash ≤ 6 и dHash ≤ 10, мульти-индекс по 8 байтам) | `Grouping.kt` → `similarGroups` | как есть + временное окно кандидатов |
| Пары RAW+JPEG | `Grouping.kt` → `rawPairs` | как есть |
| Копии «телефон ↔ Диск» | `analysis/Copies.kt` | как есть |
| Хэши pHash/dHash | `Hashes.kt` | как есть |
| Качество: резкость по тайлам 8×8 (верхняя четверть дисперсий Лапласиана), шум (MAD), экспозиция (p5–p95), пересвет | `analysis/Quality.kt` | как есть, затем добавить лица (ML Kit) в итоговую оценку |
| Причины выбора и статус «оценки близки» (разрыв < 0.02) | `Quality.kt` → `recommend` | как есть; правило «≤ 30 % серии» заменяем на «лучший + решение пользователя» |
| Защита последней копии | `deletion/DeletionEngine.kt` → `protectedLastCopy` | логику проверок переносим; исполнение — через корзину (`createTrashRequest`, Диск `permanently=false`) |
| Клиент API Диска, каталог, инкрементальная синхронизация | `disk/DiskApi.kt`, `disk/DiskCatalog.kt` | как образец; в Pickly — TypeScript в приложении (сеть) + Kotlin только для вычислений |
| Хэши MD5/SHA-256 потоково | `disk/Md5.kt`, `disk/Sha256.kt` | как есть |
Не переносим: экраны Compose, Room, фоновые воркеры, оркестратор, посредник отзывов —
у Pickly своя архитектура (Expo, SQLite, Yandex Cloud).
